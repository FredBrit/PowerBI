# Предположим, что у нас есть таблица фактов, также две таблицы (таблица уникальных дат с Date_ID и таблица уникальных категорий с Category_ID)
# Есть визуализация плоская таблица с группировкой по категории, дате, году, номеру месяца и два фильтра (Категории с текстовым поле Category и Год с числовым полем Year)
# Мы фильтруем по Category

### Шаг 1 — FE находит значение в словаре измерения
Когда вы в визуализации ставите фильтр Category = "Category_1", происходит не одно, а несколько действий, разделенных между FE и SE:
FE выполняет запрос к таблице Categories:
  SELECT CategoryID FROM Categories WHERE Category = 'Category_1'
  
Результат: CategoryID = 1
Это точечный lookup в словаре — занимает микросекунды. FE получает integer-идентификатор.

### Шаг 2 - FE передает bitmap в SE
FE формирует bitmap-фильтр для таблицы фактов:
Fact[CategoryID] IN (1)
→ Bitmap: [0,1,0,1,1,0,0,1,...]  (50 млн бит, где 1 = строки с CategoryID=1)

Этот bitmap передается в Storage Engine. SE никогда не видит текст "Category_1" — он работает только с integer-кодами

### Шаг 3 — SE применяет bitmap к фактам
Fact таблица:
  CategoryID: [1, 2, 1, 3, 1, 2, ...]
  Amount:     [100, 200, 150, 300, 120, 250, ...]

Bitmap:       [1, 0, 1, 0, 1, 0, ...]
Результат:    [100, -, 150, -, 120, -, ...]

Это побитовое AND между bitmap фильтра и bitmap колонки CategoryID. 
Операция выполняется на уровне CPU-регистров (AVX-инструкции), обрабатывает 256-512 бит за такт.

### Шаг 4 — SE агрегирует отфильтрованные строки
SUM(Amount) по оставшимся строкам → результат возвращается в FE

Гроупбай в самом конце


Движок                     Отвечает за                                                        Примеры операций
FE (Formula Engine)        DAX-вычисления, итерации, виртуальные таблицы, JOIN-логика         SUMX, FILTER, CALCULATE, трансляция фильтров
SE (Storage Engine)        Сканирование колонок, bitmap-операции, агрегации                   SUM, COUNT, WHERE, GROUP BY на физическом уровне


### Когда FE становится проблемой
FE > 30-50% от Total — сигнал, что:
- Используются итераторы (SUMX, AVERAGEX)
- Сложные FILTER с условиями по строкам
- Виртуальные таблицы (SUMMARIZE, ADDCOLUMNS в DAX)
- Нужно переписывать DAX, а не данные

### Главное правило: если SE > 90% — оптимизируй данные. Если FE > 30% — оптимизируй DAX.


### Основные сценарии

1. Фильтр по категории — побеждает плоская модель
Почему плоская быстрее?

В плоской модели столбец Category — это текст, который хранится в словаре (Dictionary Encoding).

Фильтр Category = 'Category_5' — это поиск по словарю (очень быстрая операция, O(log n)).

Движок находит ID категории в словаре, строит битмап и применяет его к столбцу CustomerID за один проход.

Почему нормализованная медленнее?

В нормализованной модели фильтр по категории требует JOIN с таблицей Categories.

VertiPaq должен:

Найти CategoryID для 'Category_5' в таблице Categories (быстро).
Применить этот ID к таблице Facts через отношение (операция Lookup).
Это создаёт дополнительный слой обработки, который увеличивает SE CPU (375 мс против 125 мс).
Вывод: Если фильтры всегда по категории, плоская модель выгоднее, потому что не нужен JOIN.


2. Фильтр по году — побеждает нормализованная модель (самая большая разница)
Почему нормализованная быстрее?

Год — это низкая кардинальность (всего несколько уникальных значений).

В нормализованной модели таблица Dates имеет всего 365 строк (по одной на каждый день).

Фильтр Year = 2022 сканирует эти 365 строк мгновенно (17 мс по вашему первому тесту).

Затем VertiPaq строит битмап из 365 DateID и применяет его к Facts.

Это Segment Elimination — движок пропускает целые сегменты данных, не содержащие 2022 год.

Почему плоская медленнее?

В плоской модели столбец Год хранится в каждой строке фактов.

Фильтр по году требует сканирования всего столбца Год (миллионы строк), чтобы найти 2022 год.

Это полный перебор (Full Scan), который даёт SE CPU = 3 156 мс.

Вывод: Для фильтров по высокоуровневым измерениям (год, месяц) нормализованная модель критически важна.



3. Фильтр по году + категории — побеждает нормализованная модель (но разница минимальна)
Это самый интересный результат! Давайте разберёмся, почему разница сократилась до 1.2x.

Что произошло?

В плоской модели: фильтр по категории (быстрый) сильно сократил количество строк.

После применения фильтра по категории осталось, например, 10% данных.

Затем фильтр по году применяется уже к отфильтрованному подмножеству.

Итоговое время = 165 мс (что близко к 167 мс для одного фильтра по категории).

В нормализованной модели: фильтры по году и категории применяются параллельно через битмапы.

Два битмапа (Year=2022 и Category='Category_5') пересекаются (AND) до сканирования фактов.

Это даёт ещё большее сокращение данных перед основным сканированием.

Почему разница не 2.7x, как в случае с годом?

Потому что фильтр по категории в плоской модели уже сократил данные до небольшого объёма.

После этого добавление фильтра по году не сильно увеличивает нагрузку.

Вывод: Если фильтры всегда включают категорию, плоская модель может быть приемлемой. Но если есть отчёты только по году — нормализованная модель обязательна.


4. Сумма Amount за 2022 год (SUM) — огромная победа нормализованной модели

Почему такая большая разница?

В плоской модели: SUM требует сканирования столбца Amount (все строки, где год = 2022). Но перед этим движок должен отфильтровать данные по году. Фильтрация по году в плоской модели — это Full Scan столбца Год (3 156 мс в тесте DCOUNT). В сумме: сканирование года + сканирование Amount.

В нормализованной модели:

Сначала сканируется маленькая таблица Dates (365 строк) для поиска 2022 года.
Строится битмап для 2022 года.
Битмап применяется к Facts через отношение Facts[Date] = Dates[Date].
Сканируется только столбец Amount в отфильтрованных строках.
Ключевой вывод: SE CPU = 188 мс против 1 297 мс — это главное доказательство эффективности битмапов. VertiPaq не сканирует все строки Facts, а только те, которые попадают в битмап.


5. Группировка по месяцам — неожиданная победа плоской модели
Почему плоская модель оказалась быстрее в 4.3 раза?

В плоской модели:
Данные уже денормализованы — все столбцы (Год, Месяц, Amount) находятся в одной таблице.

Группировка по Год и Месяц требует одного сканирования таблицы Optimized.

Движок строит хэш-таблицу для группировки (90 уникальных комбинаций год+месяц).

SE CPU = 375 мс — это время одного сканирования + построение хэша.

В нормализованной модели:
Группировка требует JOIN между Facts и Dates.

Это означает, что движок должен:

Просканировать Dates (маленькая таблица).
Соединить с Facts через DateID (операция Lookup).
Построить хэш-таблицу для группировки.
SE CPU = 656 мс — почти вдвое больше, чем в плоской модели.

Почему JOIN так дорог?

VertiPaq использует операцию Lookup — для каждой строки Facts он ищет соответствующий год и месяц в таблице Dates.

Это дороже, чем просто прочитать готовые значения из одной таблицы.

Дополнительно: FE = 17 мс против 6 мс — Formula Engine тоже участвует в соединении, что добавляет накладные расходы.


6. Группировка по месяцам с фильтром по году — побеждает нормализованная модель
Почему такая разница в SE CPU?

В плоской модели:
Фильтр по году = Full Scan столбца Год (все строки).
Затем группировка по Месяц + SUM по Amount.
SE CPU = 1 884 мс — это сумма сканирования года + сканирования месяца + сканирования суммы.

В нормализованной модели:
Фильтр по году = сканирование 365 строк в Dates.
Битмап применяется к Facts.
Группировка по месяцу + SUM по Amount.
SE CPU = 334 мс — битмап уже сократил данные до 2022 года, поэтому группировка работает с меньшим объёмом.

Ключевой вывод: Когда есть фильтр, нормализованная модель становится быстрее, потому что битмап сокращает данные до группировки.

7. Фильтр по диапазону дат — огромная победа нормализованной модели (15.2x!)

Это самый показательный тест! Давайте разберём, почему такая разница.

В плоской модели:
Фильтр Date >= DATE(2022,6,1) AND Date <= DATE(2022,6,10) требует сканирования столбца Date в таблице Optimized.

Date — это тип datetime (8 байт), который плохо сжимается.
VertiPaq должен проверить каждую строку на соответствие диапазону.
SE CPU = 1 047 мс — полный перебор.

В нормализованной модели:
VertiPaq построил 3 подзапроса (TTable2, TTable3, TTable1):

$TTable2 — создаёт индекс (SIMPLEINDEXN) для Date >= 2022-06-01
$TTable3 — создаёт индекс (SIMPLEINDEXN) для Date <= 2022-06-10
$TTable1 — применяет оба индекса через ININDEX и считает SUM
Что такое SIMPLEINDEXN? Это создание битмапа для условий диапазона. Вместо сканирования всех строк, VertiPaq создаёт индексы для каждого условия, а затем пересекает их (VAND = AND).

SE CPU = 16 мс — это почти мгновенно, потому что:
Таблица Dates сканируется целиком (маленькая).
Индексы строятся на лету (быстро).
К Facts применяются уже готовые битмапы.

Ключевой вывод: Для фильтров по диапазонам дат нормализованная модель критически важна. Это самое сильное преимущество звездообразной модели.



### Когда плоская модель лучше:
Группировки без фильтров (как в вашем тесте).
Когда нужно много столбцов из одной таблицы (SELECT *).
Когда нет фильтров по измерениям с низкой кардинальностью (год, месяц).


### Когда нормализованная модель лучше:
Фильтрация по измерениям (год, категория).
Агрегации с фильтрами (SUM + WHERE по году).
Когда данные растут (больше 10 млн строк) — битмапы работают эффективнее.

### Фундаментальный вывод для VertiPaq
Scan (сканирование одной таблицы) — быстрее, если данных немного и нет сложных фильтров.
Lookup + Bitmap (соединение через отношения) — быстрее, если есть фильтры по измерениям, потому что позволяет пропускать сегменты.

VertiPaq выбирает стратегию автоматически на основе:
-Кардинальности столбцов.
-Размера таблиц.
-Наличия отношений.
