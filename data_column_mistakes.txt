### Общие положения

1. Является ли количество столбцов критичным для «широкой» витрины?
Да, критичным — и гораздо сильнее, чем количество строк!

Power BI работает на поколоночном движке (Columnar Database). В отличие от классических реляционных СУБД (PostgreSQL, MS SQL), которые хранят данные строками (Rowstore), VertiPaq сжимает и хранит каждый столбец независимо.

# Чем опасна «широкая» витрина (Wide Table):
Каждый столбец = отдельная структура данных. Для каждого столбца создается свой словарь (Dictionary) и индекс. 100 столбцов сжимаются в 100 раз дольше, чем 10 столбцов, даже при одинаковом числе строк.

# Проблема SELECT * в визуалах. Если визуал запрашивает данные из таблицы, движок считывает только нужные столбцы. Но если модель загружена 80 неиспользуемыми столбцами, они тупо съедают RAM на сервере (Premium / Fabric Capacity).

# Худшее сжатие (RLE). Алгоритм сжатия RLE (Run Length Encoding) ищет повторяющиеся подряд значения. Чем больше столбцов в витрине, тем чаще эти таблицы генерируются из плоских JOIN'ов на стороне DWH, что разрушает сортировку и ухудшает сжатие.

# Золотое правило Senior'а: Избавься от концепции «одной большой витрины» (One Big Table / OBT) в In-Memory модели. Модель Power BI должна быть звездой (Star Schema).




2. Что, если ID (или детализация уровня транзакции) БИЗНЕСУ КРИТИЧНО?
Иногда бизнес говорит: «Мне обязательно нужно уметь проваливаться до конкретной транзакции / чека / договора!».

Если удалять ID нельзя, у Senior-архитектора есть 3 главных паттерна:

# Паттерн А. Разделение на Заголовок и Строку (Header / Line Detail)
Очень часто уникальным является не один ID, а комбинация (например, OrderNumber + LineNumber).

Ошибка: Хранить составной ключ строкой ORD-12345-01 (кардинальность = 100%).

Решение: Вынести атрибуты заказа (Дата, Клиент, Статус) в таблицу Fact_Orders (10 млн строк), а детали позиции — в Fact_OrderLines (50 млн строк) и связать их по СУРРОГАТНОМУ целочисленному ключу (Integer OrderID). Целые числа сжимаются движком через Value Encoding в разы лучше, чем GUID/строки.

# Паттерн Б. Агрегация + Drillthrough (Сквозная детализация)
В основную In-Memory модель загружаются агрегированные данные (например, сгруппированные по Дням, Клиентам и Категориям). Это уменьшает 50 млн строк до, условно, 2 млн.

Вся аналитика, KPI и дашборды работают мгновенно на агрегатах.

Настраивается Drillthrough (детализация): когда пользователь хочет увидеть конкретные транзакции по выведенному клиенту, Power BI совершает DirectQuery запрос прямо в базу данных (SQL/Snowflake) только для выбранного среза и выводит таблицу из 20 строк.

# Паттерн В. Composite Models (Гибридная модель)
Горячие / Агрегированные данные лежат в Import Mode (VertiPaq).

Детальная таблица с транзакционными ID лежит в DirectQuery Mode (в СУБД).

VertiPaq сам объединяет их на лету.


# Наиболее частые ловушки, которые бросаются в глаза

Ловушка №1: TransactionGUID (Уникальный текст)

Проблема: Кардинальность = 50 000 000.

Результат в VertiPaq: Размер словаря (Dictionary Size) этой одной колонки займет до 80-90% всей памяти модели!

Решение Senior'а: Удалить из аналитической модели (зачем аналитикам первичный ключ каждой строки в In-Memory?).


Ловушка №2: TransactionDateTime (Дата + Точное Время)

Проблема: Кардинальность из-за секунд и миллисекунд стремится к десяткам миллионов.

Результат в VertiPaq: Сжатие по алгоритму RLE (Run Length Encoding) здесь не сработает вообще. Кодирование свалится в Hash Encoding.

Решение Senior'а: Разделить на 2 колонки — Date (кардинальность ~1095 дней) и Time (или вообще округлить время до часов/минут).


Ловушка №3: Amount (Float64 / Число с плавающей точкой)

Проблема: В отличие от целых чисел или фиксированной точки (Decimal / Fixed Decimal Number), числа с плавающей точкой хреново сжимаются движком VertiPaq.

Решение Senior'а: В Power Query явно сменить тип данных на Fixed Decimal Number (Currency). Это переведет движок на Value Encoding, что существенно сократит размер.


Ловушка №4: Невидимые скрытые таблицы дат (Auto Date/Time)
по умолчанию в Power BI Desktop включена галочка «Автоматическая дата и время».

В чем уловка: Для КАЖДОГО столбца с типом Date или DateTime Power BI скрыто создает отдельную таблицу дат в памяти с диапазоном от минимального года до максимального!

Результат: На модели с 10 датами у тебя появится 10 скрытых таблиц, раздувающих размер.

Решение: Всегда отключать Auto Date/Time в настройках файла и использовать единую правильную таблицу измерений Dim_Date (Календарь).


Ловушка №5: Избыточная точность дробных чисел
Если столбец Price или Discount имеет вид 12.3456789:

Высокая точность убивает сжатие Value Encoding, переводя столбец в Hash Encoding.

Решение: Округлять до необходимым бизнесу знаков (обычно 2 знака) еще в Power Query или SQL.


Ловушка №6: Текстовые поля с длинным описанием (Комментарии, Адреса)
Поле OrderComment («Клиент попросил перезвонить после 18:00») на 50 млн строк может весить больше, чем вся остальная модель вместе взятая.

Решение: Удалять текстовые комментарии из аналитической модели. Для них используется подход DirectQuery / Drillthrough.


Ловушка №7: Неявный Context Transition из-за вычисленных столбцов (Calculated Columns)
Создание новых столбцов через DAX (а не в Power Query/SQL) во время загрузки:

Вычисленные столбцы не сжимаются так же эффективно, как загруженные напрямую, потому что VertiPaq создает их после основного сжатия.

Решение: Все столбцы трансформируем ДО загрузки в VertiPaq (в SQL или Power Query). В DAX пишем ТОЛЬКО МЕРЫ (Measures).
