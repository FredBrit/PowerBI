# Базовые концепции VertiPaq
Поколоночное хранение (Columnar Storage)
В отличие от реляционных СУБД, которые хранят данные строками, VertiPaq разбивает таблицу на отдельные независимые столбцы.

Как это работает: Каждая колонка сжимается, кодируется и индексируется изолированно от других.

Влияние: Если визуал запрашивает только SUM(Amount) по Category, VertiPaq считывает из RAM только 2 столбца, полностью игнорируя остальные 50.

Кардинальность (Cardinality)
Это количество УНИКАЛЬНЫХ значений в столбце.

Пример: В столбце Gender кардинальность = 2 (M, F). В TransactionGUID на 50 млн строк кардинальность = 50 000 000.

Влияние: Это главная метрика, определяющая размер модели. Чем выше кардинальность, тем больше размер словаря и тем хуже работает сжатие.


# Анатомия колонки в памяти (Из чего состоит столбец)
В VertiPaq колонка состоит из одного словаря и одного массива индексов (структуры данных).

[ ИСХОДНЫЙ ТЕКСТ (50 млн строк) ]
                  │
                  ▼
┌─────────────────────────────────────────────────────────┐
│                    СТРУКТУРА КОЛОНКИ                    │
├────────────────────────────┬────────────────────────────┤
│     1. СЛОВАРЬ (Dict)      │   2. МАССИВ ДАННЫХ (Data)  │
│    (Уникальные значения)   │      (Сжатые ID строк)     │
├────────────────────────────┼────────────────────────────┤
│   ID 0 = "Category_A"      │   Строка 1  ➔  ID 0        │
│   ID 1 = "Category_B"      │   Строка 2  ➔  ID 1        │
│                            │   Строка 3  ➔  ID 0        │
│                            │   ...                      │
└────────────────────────────┴────────────────────────────┘

1. Единый Словарь (Dictionary)
Это хэш-таблица уникальных значений. Она хранит только уникальные строки и присваивает каждой короткий числовой код (ID):
"Category_A": 0,"Category_B": 1

Смысл: Вместо того чтобы 50 миллионов раз хранить тяжелую текстовую строку "Category_A" (которая весит десятки байт), мы храним её всего 1 раз.

2. Массив Данных / Индекс (Data Array / Primary Data)
Это просто список чисел (ID из словаря), идущих в том же порядке, что и строки в твоей таблице.
Для нашего примера этот массив будет выглядеть так:
[0, 1, 0, 0, 1, 0]

Смысл: Вместо строк VertiPaq хранит плоский массив крошечных целых чисел (0 и 1). Числа занимают считанные биты памяти!

3. А где же тут сжатие RLE?
А вот поверх этого Массива Данных [0, 1, 0, 0, 1, 0] включается сжатие RLE (Run-Length Encoding).
Если бы у нас после сортировки данные шли подряд: [0, 0, 0, 0, 1, 1], VertiPaq сжал бы этот Массив Данных в две пары:
Значение 0 повторяется 4 раза
Значение 1 повторяется 2 раза
В памяти для 6 строк хранятся всего 4 числа: (0, 4) и (1, 2).

# Типы кодирования (Encoding Types). Перед сжатием VertiPaq выбирает, как именно превратить значения столбца в суррогатные ID:
1. Value Encoding (Числовое кодирование)

Для чего: Для чистых целых чисел и валют (Fixed Decimal).
Как работает: Движок не строит словарь! Он находит математическое смещение (Base Value) и хранит только разницу.
Пример: Значения [1000, 1002, 1005]. Base Value = 1000. В память пишутся числа [0, 2, 5].
Плюсы: Словаря НЕТ вообще! Операции агрегации (SUM, AVG) выполняются мгновенно прямо на уровне железа процессора (SIMD-инструкции).

2. Hash Encoding (Хэш-кодирование)

Для чего: Для текстов, дат, дробных чисел (Float) и сложных типы данных.
Как работает: Создает полноценный словарь уникальных значений и подменяет строки на суррогатные ID. Далее данные хранятся как список индексов(целых чисел).
Минусы: Требует памяти под словарь. Агрегации требуют постоянного обращения к словарю, чтобы сопоставить индекс и реальные данные которые находятся в словаре.

3. Hierarchy Encoding (Иерархическое кодирование)

Создается для поддержки связей и иерархий (например, детализация дат Год -> Месяц -> День).

# Алгоритмы сжатия (Compression)
После того как колонки закодированы (через Value или Hash Encoding), в дело вступает главный алгоритм сжатия VertiPaq — RLE (Run-Length Encoding).RLE (Сжатие повторяющихся длин)
Как работает: Вместо записи [A, A, A, A, B, B] RLE записывает пары (Значение, Количество) -> (A, 4), (B, 2).
От чего зависит эффективное RLE:
Сортировка данных: Если одинаковые значения идут подряд, RLE сжимает 10 млн строк в пару байт. 
Если значения в перемешку (A, B, A, B, A, B), RLE бессилен и только увеличит размер!
Низкая кардинальность: Чем меньше уникальных значений, тем длиннее "цепочки" повторов.


# Во что столбцы преобразуются в модели (Data Types Matrix)
Тип данных, который ты выбираешь в Power Query, напрямую определяет, как VertiPaq упакует колонку.
Тип данных в Power Query | Тип в VertiPaq | Тип кодирования | Поведение словаря и RLE 

Fixed Decimal / Currency | Int64 (умноженный на 10 000) | Value Encoding | Словаря нет. Идеальное сжатие и молниеносные математические операции.
Whole Number (123) | Int64 | Value Encoding | Словаря нет. Сжимается идеально.
Decimal Number / Float (1.2) | Double | Hash Encoding | Создается словарь. Неточности с плавающей точкой усложняют RLE.
Text (ABC) | String | Hash Encoding | Огромный словарь, если кардинальность высокая.
Date (📅) | Int64 (число дней с 1899-12-30) | Value / Hash | Кардинальность мала (~1000 значений на 3 года). Сжимается великолепно.
DateTime (📅🕒) | Double (Дни + дробная часть времени) | Hash Encoding | Катастрофа. Миллисекунды раздувают словарь до миллионов строк, RLE не работает.
